## 2. In-Depth Investigation of Token Accounting Discrepancies

### The Discrepancy
In Phase 1 initial runs, token accounting displayed apparent discrepancies:
- **Baseline:** prompt = 12,240, completion = 285, reported total = 13,430 (gap: +905)
- **Modified:** prompt = 15,456, completion = 330, reported total = 16,772 (gap: +986)

### Root Cause Analysis & Mathematical Proof
By inspecting the raw `usage` payload returned by the OpenAI-compatible proxy (`http://127.0.0.1:8045/v1`) for `openai/gemini-3.1-pro-high`, each response message contains:
```json
{
  "prompt_tokens": 1795,
  "completion_tokens": 44,
  "total_tokens": 1864,
  "completion_tokens_details": {
    "reasoning_tokens": 25
  }
}
```
Notice: `1795 (prompt) + 44 (completion) + 25 (reasoning) = 1864 (total)`.

The local proxy reports tokens according to the following strict relationship:
$$\text{total\_tokens} = \text{prompt\_tokens} + \text{completion\_tokens} + \text{reasoning\_tokens}$$

- `prompt_tokens`: Raw input prompt and message history tokens.
- `completion_tokens`: Visible generated text / tool call tokens emitted by the model.
- `reasoning_tokens`: Internal thinking / Chain-of-Thought (CoT) reasoning tokens generated by the Gemini model.
- `total_tokens`: The exact sum of all three categories.

In the initial Baseline trajectory:
$$\sum \text{reasoning\_tokens} = 465 + 39 + 23 + 105 + 86 + 77 + 110 = 905$$
$$12,240 + 285 + 905 = 13,430 \quad (\text{Exact Match})$$

In the initial Modified trajectory:
$$\sum \text{reasoning\_tokens} = 589 + 50 + 25 + 96 + 61 + 22 + 36 + 107 = 986$$
$$15,456 + 330 + 986 = 16,772 \quad (\text{Exact Match})$$

In all subsequent Phase 1.1 validation experiments, `token_formula_verified == True` was asserted and confirmed on every single run.

## 3. Audit & Algorithmic Hardening of LoopDetector

### A. Content-Based Change Detection & mtime Resilience
- **Vulnerability Identified:** Previously, file changes were detected by comparing `(file_path, st_size, st_mtime_ns)`. If a tool touched file timestamps without modifying contents (`os.utime`, compiler passes, editors), `st_mtime_ns` changed, triggering a false repository reset and failing to detect an unproductive loop.
- **Solution:** Upgraded `get_repo_fingerprint()` to use content-based SHA-256 hashing cached by `(mtime_ns, size)`. If a file's mtime changes while its content remains unchanged, its SHA-256 hash is re-verified from the bytes and found identical. The repo fingerprint remains constant, preventing false resets.

### B. Ephemeral File Filtering
- Filtered ephemeral build and execution artifacts from repo hashing:
  - Directories: `.git`, `__pycache__`, `.pytest_cache`, `.venv`, `.mypy_cache`, `.tox`, `.eggs`, `.ruff_cache`, `.cache`, `htmlcov`, `build`, `dist`.
  - File patterns: `.pyc`, `.pyo`, `.log`, `.traj.json`, `.swp`, `.tmp`, `.bak`, `.coverage`, `.coverage.*`, `*.egg-info`.
- Writing logs or test bytecode during test runs no longer resets consecutive failure streaks.

### C. Selective Repository Scanning
- **Optimization:** Previously, `get_repo_state()` executed a full directory walk on every action.
- **Solution:** Repository scanning is now evaluated conditionally:
  - If the current action differs from the previous action (`norm_cmd != last_cmd` or `returncode != last_returncode` or `out_fp != last_out_fp`), the streak is already broken by command/output divergence.
  - The repository fingerprint is only re-evaluated when an action is a candidate repetition of the previous action.
  - Combined with stat-based hash caching, per-step overhead is negligible (< 1ms).
